# TrainGrid database audit

**24 November 2026.** Reviewed main at `9a11c59`, confirmed against the remote at the start of the audit. The highest-priority fix binds a new membership admission to an unused invitation. Three further fixes close gaps in follow visibility, workout document validation and concurrent daily limits. All four preserve public RPC signatures, generated types and existing training history.

## Scope and evidence

Two separately named local Supabase projects ran PostgreSQL 17 with synthetic accounts and the repository seed. The first replayed all 15 baseline migrations, then upgraded in place. The second started empty and replayed the full 17-migration chain. The audit used the actual PostgREST/Auth services, role-scoped SQL, browser flows, catalog inspection and a representative authenticated query plan. Results describe this checkout. Hosted grants, historic rows, database settings, traffic and latency were unavailable for comparison.

### Schema and relationship overview

| Area | Relationships and invariants | Assessment |
|---|---|---|
| Identity and membership | `auth.users → profiles` is one-to-one by UUID. `revoked_at` distinguishes suspension from account deletion. Active membership gates training and social access. A revoked member can read their own identity row so the app can determine access status. | Keep authentication and membership distinct. Verified provider email supports admission. The persistent identity for ownership is the auth UUID. |
| Invitations and feedback | `invite_requests` has a partial unique pending-email index. `invitations` has one live normalized email, optional inviter/recipient references and multiple delivery attempts. `member_feedback` belongs to a profile. | Requests, decisions and provider outcomes have different lifetimes. Delivery reservation locks the invitation row. The retention migration schedules expiry even without incoming requests. Feedback is insert-only for members. |
| Routines and calendar | GLOBAL routines have no owner, PERSONAL routines require one. A routine owns ordered items with unique positions. Each session belongs to a member and optionally references the source routine. | Relational editing and immutable-at-scheduling JSON copies serve different jobs. Deleting a routine removes its items, clears provenance and preserves the planned occurrence. Calendar dates and optional wall-clock times fit untimed training and local weeks. |
| Performed workouts | A session has zero or one workout log via unique `session_id`. Log ownership is independently scoped by member and checked against the source session at insert. Session deletion cascades to its log. | Versioned JSONB keeps performed sets together. A quick workout shares the session model. The existing start RPC atomically creates both rows with a retry key. Finish locks the log and records the quick name/duration in the same transaction. |
| Social identity and relationships | A profile optionally owns one social profile. Directed follows use a composite PK and disallow self-follow. Public/private visibility determines automatic acceptance or approval. | Keeping social optional supports solo use. Unique relationship keys prevent duplicate follows. The new visibility lock fixes an ordering gap. |
| Posts and reactions | Each authored post contains a limited snapshot. The private source-session FK becomes NULL on deletion. A like is unique per post/member. Comments are independent authored rows. Deleting the social identity or post cascades through its dependent rows. | Published summaries can survive a calendar edit/delete without exposing the underlying log. Leaving social preserves the training plan. Existing reaction policies distinguish authorship, post visibility and moderation rights. |

The schema uses UUIDs, snake_case, constrained text states, date/time for calendar placement and timestamptz for instants. Composite relationship keys and one-to-one identity keys express cardinality directly. The database-design skill also favors generalized `id` keys, timestamp conventions and indexes on referencing FKs. Converting these PostgreSQL instants to integers or adding surrogate IDs to likes/follows would increase migration risk without solving an observed defect. Existing nullability for untimed sessions, global owners and deleted source links carries product meaning.

## Verified findings and remediation

| Severity | Finding and evidence | Root cause | Applied change and acceptance evidence |
|---|---|---|---|
| **High** | A consumed invitation could authorize a different verified identity associated with the same email. The prior admission function filtered by email and revocation only. A delivery record can also retain its acceptance timestamp after its auth FK becomes NULL. | Admission treated a live email reservation as an unused invitation. The stored recipient and the provisioned member could diverge. | Require both acceptance fields to be empty when admitting a member. Existing active members retain their fast path. A fresh invitation still works after revocation. Deleting the accepting account retires its invitation (keeping `accepted_at`), so the address can be invited again in one step; the migration retires invitations already orphaned this way. The new pgTAP cases cover distinct identities, retained acceptance history and re-invitation. |
| **Medium** | A newly public profile could retain a pending request. In a controlled two-connection run, the owner made a private profile public while another member followed. The committed relation was pending before the fix and accepted afterward. | Follow insertion read the old visibility without locking the profile. The visibility transition could finish its pending-request sweep before seeing that follow. | A per-followee advisory lock orders the two: a follow takes it shared before reading visibility, and only an actual private → public change takes it exclusively. Concurrent followers never wait on each other, and ordinary profile edits (bio, name, avatar) never wait on follows. pgTAP checks which lock each operation holds; the controlled two-connection check covers both orders. |
| **Medium** | Calendar snapshots and log entries could lack `version` or `items` despite the documented envelope. The original CHECK predicate evaluated to SQL UNKNOWN for missing keys. The session mapper throws on unreadable input, while log mapping can show empty progress. | PostgreSQL CHECK accepts UNKNOWN. Existing shape constraints tested types and values only when present. | New invoker triggers check key presence on insert or changed document. Original type/size checks still apply. Legacy payloads can be retained during unrelated edits and replaced intentionally. pgTAP covers missing keys, valid defaults, owner repair and isolation from another member. |
| **Medium** | Feedback, follows, session posts and comments used a count-then-allow daily limit. Independent transactions at READ COMMITTED can both see the same remaining slot. | The counts had no serialization point per writer. The limits for public invite requests and invitation-email delivery already use separate locking mechanisms. | An early BEFORE INSERT trigger obtains a transaction advisory lock keyed by the table and the calling member (the row's writer only for the service role, so a row rejected by RLS cannot hold someone else's lock) before the existing counter runs. PostgreSQL fires same-timing triggers by name, so pgTAP fails if any BEFORE INSERT trigger on these tables sorts ahead of the lock. The API regression fills nine feedback slots, submits two ordinary messages concurrently and verifies exactly one succeeds. This is a concurrency invariant, not evidence of incidents in production. |

The changes are in [the admission, document and quota migration](../supabase/migrations/20261125010000_database_audit.sql) and [the follow-visibility migration](../supabase/migrations/20261125020000_follow_visibility.sql). The local regressions are in [pgTAP](../supabase/tests/database/16_database_audit.test.sql) and [the concurrent limit test](../tests/integration/member-limits.test.ts).

## Security and authorization

The baseline catalog showed **14 of 14 public tables with RLS enabled** and **37 policies**. The app generally scopes private queries by the authenticated owner and uses that owner's client. Database policies enforce the same boundary for direct API reads and writes. Column grants protect fields such as session ownership and post provenance. In particular, a grant for a whole operation on a table and the policy deciding which rows it affects are separate checks.

The function-exposure suite examines effective privileges in the catalog. In the tested public schema, anonymous users have no executable functions, and `accept_invitation` is the only SECURITY DEFINER function executable by authenticated users. Its empty search path, schema-qualified relations, verified identity check and invitation lock are preserved. The new document and quota trigger functions are private, invoker-rights and unavailable for direct member execution. The follow trigger retains its existing definer rights and ACL. The review included private visibility/count helpers and the admin-only service-role operations. The service role remains a trusted boundary that bypasses RLS and requires server-side administration checks.

The existing pgTAP matrix exercises member, other member, anonymous and revoked roles, global/personal routine ownership, private schedules, social audience changes, member revocation and post moderation. Later migrations replace several initial policies and functions. The security conclusions above use the final catalog and executed assertions, rather than assuming the first policy definition still applies. These tests establish the covered access decisions. They are not a certification of hosted configuration.

## Performance and access patterns

- **Week view.** An authenticated EXPLAIN ANALYZE with 2,000 synthetic daily sessions selected seven dates through `scheduled_sessions_user_id_date_idx`, then used an incremental sort. The execution reported nine shared buffer hits and about 1.9 ms locally. The predicate follows the owner/date range used by `listSessionsForWeek`. This sample projected calendar columns only. Transfer and decoding of full app snapshots and the embedded log were outside the measurement. Keep the existing index.
- **Library and sessions.** PostgREST embeds workout items in routine reads. Session details and the focused player read bounded sets of related data. The library reads a bounded candidate set before filtering and discloses truncation. At larger personal-library sizes, validate whether search should filter before the cap. The inspected list queries provided no evidence requiring a per-item fetch redesign.
- **Feed and export.** Feed uses an author/time/id index and a composite keyset cursor. Reaction totals are correlated counts inside the query, with indexes starting on post ID. This avoids a round trip for every displayed post, but counts still cost database work. Export v6 uses stable page ordering. Offset pages from separate API calls can span different snapshots during concurrent edits. A consistent point-in-time export would be a separate product guarantee.
- **FK coverage.** The baseline catalog found three referencing columns without a leading index: `invitations.invited_by`, `invitations.accepted_by` and `invitation_email_deliveries.requested_by`. Account deletion can scan them to perform SET NULL. These are low-volume administrative relations in the intended deployment. Inspect row counts and deletion plans before adding indexes. No workload evidence justified three new write-maintained indexes.
- **Concurrency cost.** Daily-limit locks serialize same-member inserts into the same table until commit. A hash collision can add a wait. Making a profile public waits for in-flight follows of that profile; other profile edits do not. Keep API transactions short. The audited quota behavior assumes the Data API's READ COMMITTED transaction model.

## Remaining risks and manual release steps

1. **Review historical state before rollout.** Count document rows with missing envelope keys using the aggregate below. This check reveals no member content. It only detects missing keys. Investigate affected records separately with owner approval. The migrations neither rewrite historic JSON nor automatically change any existing membership or social relationship.

   ```sql
   select 'sessions' as source, count(*) as missing_keys
   from public.scheduled_sessions where not (snapshot ?& array['version','items'])
   union all
   select 'workout_logs', count(*)
   from public.workout_logs where not (entries ?& array['version','items']);
   ```

2. **Handle anomalies explicitly.** A consumed invitation stays consumed when its accepted account has been removed: it is retired automatically, so the admin can issue a fresh invitation to the same email directly. Existing active profiles still sign in. Review uncertain historic admissions using trusted administrative records before making an access decision. Do not infer account ownership solely from a present-day email. Existing pending requests on public profiles can be reviewed individually.
3. **Apply in order in an approved release window.** Ensure the target already has the baseline chain through `20261125000000`, the required Supabase auth roles/extensions, and working backup/restore procedures. Apply `20261125010000`, then `20261125020000` using the normal migration mechanism. Function replacement and trigger installation require brief relation locks. There is no table rebuild, backfill or public API signature change. Keep a bounded lock wait and retry at a quieter time if necessary.
4. **Verify the actual behavior.** Compare migration history and run the release schema check. The API manifest describes public shape, so it could not prove that private triggers or replacement function bodies were installed. Since `20261127000000_release_migration_history`, the check also compares the project's migration history with the build's migrations, so a skipped migration of that kind is reported; it still does not compare the installed SQL itself. Run pgTAP/integration in a release-matched isolated environment. Smoke test normal invitation acceptance, scheduling, workout save and follow approval with designated test accounts before broadening access. No migration or release operation was performed against production during this audit.
5. **Keep repair and rollback separate.** If corrective DDL is needed, prepare a reviewed forward migration identifying the specific trigger/function involved. Reinstating the previous admission logic would reopen the identity issue. No automatic rollback or deletion of suspect rows is proposed.
6. **Residual design boundaries.** The JSON check covers the versioned envelope. App validators remain responsible for detailed item/set structure. Parallel saves from two devices no longer use last-write-wins for workout progress: since `20261126000000_workout_save_conflicts`, a save from a stale version is refused and the member chooses. Daily quota counts reflect retained rows and do not constitute a permanent event ledger. The remaining limits warrant separate requirements and evidence before introducing new tables or historical rewrites.
